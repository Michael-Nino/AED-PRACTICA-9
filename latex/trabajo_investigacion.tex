\section{Trabajo de Investigación}

\subsection{Sistema 1: SQLite — B-Tree para indexación de bases de datos embebidas}

\subsubsection{Problema que resuelve}
SQLite es la base de datos más usada del mundo, presente en Android, iOS, Firefox y Chrome. Necesita localizar registros en archivos de disco sin cargar todo en RAM. Cada consulta SQL debe encontrar filas en tablas que pueden tener millones de registros, almacenadas en archivos de disco que no caben enteros en memoria principal.

\subsubsection{Por qué se eligió el B-Tree}
A diferencia del BST simple (óptimo para RAM), el B-Tree almacena múltiples claves por nodo (cientos), reduciendo la altura y minimizando operaciones de E/S. Un B-Tree de orden 500 con 1 millón de registros tiene altura $\leq 3$. Esto significa que cualquier búsqueda requiere a lo sumo 3 accesos a disco, independientemente del tamaño de la base de datos.

\subsubsection{Complejidad garantizada}
Búsqueda, inserción y eliminación son $O(\log_t n)$ donde $t$ es el orden mínimo. Para SQLite con páginas de 4096 bytes, $t \approx 250$, garantizando altura $\leq 4$ para $10^9$ registros. La estructura B-Tree mantiene todas las hojas al mismo nivel (árbol perfectamente balanceado), lo que garantiza que el número de accesos a disco sea logarítmico en el peor caso.

\subsubsection{Impacto en rendimiento}
SQLite ejecuta más de 50\,000 consultas SELECT por segundo en SSD convencional gracias a la estructura B-Tree de sus índices. La implementación de SQLite usa B-Tree con páginas de tamaño fijo (generalmente 4096 bytes), donde cada nodo del árbol corresponde exactamente a una página de disco. Esto permite que el sistema operativo optimice las lecturas mediante paginación.

Diagrama de un B-Tree de orden 3 con 5 claves:

\begin{verbatim}
        [20 | 40]
       /    |    \
   [10]   [30]   [50]
\end{verbatim}

Referencia: Bayer \& McCreight (1972) DOI: 10.1007/BF00288683 + documentación oficial SQLite.

\subsection{Sistema 2: Java TreeMap — Red-Black Tree en la JVM}

\subsubsection{Problema que resuelve}
\texttt{TreeMap<K,V>} de Java provee un mapa ordenado con iteración en orden, búsqueda de rangos y sucesor/predecesor. Usado en sistemas de trading (order books) y cachés ordenados. En un order book de alta frecuencia, es necesario mantener las órdenes de compra y venta ordenadas por precio para poder ejecutar cruces en milisegundos.

\subsubsection{Por qué se eligió el Red-Black Tree}
El BST puede degradarse a $O(n)$ con inserciones ordenadas. El Red-Black Tree garantiza altura $\leq 2 \cdot \log_2(n+1)$ mediante invariantes de coloración: cada nodo es rojo o negro; ningún camino tiene dos nodos rojos consecutivos; todos los caminos a hojas tienen el mismo número de nodos negros. Estas invariantes se mantienen después de cada inserción y eliminación mediante rotaciones locales, garantizando que el árbol nunca se desbalancee significativamente.

\subsubsection{Complejidad garantizada}
Inserción, búsqueda y eliminación son $O(\log n)$ garantizado en el peor caso, no solo en promedio. Esto contrasta con el BST simple donde el peor caso es $O(n)$. La complejidad espacial es $O(n)$, igual que cualquier árbol binario.

\subsubsection{Impacto en rendimiento}
El framework LMAX Disruptor (trading de alta frecuencia) usa \texttt{TreeMap} para mantener order books con 100\,000+ órdenes activas, procesando millones de transacciones por segundo. Cada transacción requiere insertar o eliminar órdenes en $O(\log n)$, y el recorrido in-order permite obtener instantáneamente las mejores ofertas de compra y venta.

Diagrama de Red-Black Tree con 7 nodos:

\begin{verbatim}
           [20N]
          /      \
      [10N]    [30N]
      /    \    /    \
  [5R] [15R] [25R] [40R]
\end{verbatim}
Donde \textbf{N} = negro, \textcolor{red}{R} = rojo.

Referencia: Guibas \& Sedgewick (1978) DOI: 10.1109/SFCS.1978.3 + Java SE 17 TreeMap docs.

\section{Preguntas de Reflexión}

\subsection*{1. ¿Por qué el recorrido in-order de un BST produce siempre una lista ordenada ascendentemente?}
El recorrido in-order visita los nodos en el orden: subárbol izquierdo, raíz, subárbol derecho. Por la invariante BST, todos los valores del subárbol izquierdo son menores que la raíz, y todos los del subárbol derecho son mayores. Esta propiedad se mantiene recursivamente en cada subárbol. Al visitar primero completamente el subárbol izquierdo (valores menores), luego la raíz (valor medio), y luego el subárbol derecho (valores mayores), se obtiene automáticamente una secuencia ordenada ascendente. Formalmente, si $T$ es un BST con raíz $r$, entonces $\text{in-order}(T) = \text{in-order}(T_{izq}) \cdot [r] \cdot \text{in-order}(T_{der})$, donde $\cdot$ denota concatenación. Por inducción, si los subárboles producen listas ordenadas, la concatenación también lo es.

\subsection*{2. ¿Qué ocurre con la complejidad del BST cuando los datos se insertan en orden creciente?}
Cuando las claves se insertan en orden estrictamente creciente, cada nueva clave es mayor que todas las anteriores, por lo que siempre se inserta como hijo derecho del nodo más a la derecha. El árbol resultante es un árbol degenerado (una lista enlazada hacia la derecha) con altura $h = n - 1$. En este caso, las operaciones de búsqueda, inserción y eliminación tienen complejidad $O(n)$ en lugar de $O(\log n)$. Esta situación se conoce como el caso degenerado del BST. Para solucionarlo se usan árboles autobalanceados como los AVL (Semana 11) o Red-Black Trees (Semana 12), que mediante rotaciones locales mantienen la altura $O(\log n)$ en todo momento.

\subsection*{3. Compare la búsqueda en un BST, en una lista Python y en un diccionario Python. ¿En qué situaciones reales preferiría usar un BST?}
El diccionario Python (tabla hash) tiene búsqueda $O(1)$ amortizado, pero no mantiene orden. La lista tiene búsqueda $O(n)$ pero es la estructura más simple. El BST ofrece búsqueda $O(\log n)$ promedio y además mantiene los elementos ordenados. Se prefiere un BST cuando se necesitan: (a) recorrer los datos en orden ascendente, (b) consultas por rango (ej. "estudiantes con código entre 20210300 y 20210700"), (c) encontrar el sucesor o predecesor de un elemento. En el sistema de expedientes académicos de la UNAP, el BST permite listar los estudiantes ordenados por código, buscar rangos de códigos para filtrar por semestre de ingreso, y encontrar rápidamente el estudiante con el código más alto o más bajo.

\subsection*{4. ¿Por qué el Linux Kernel usa Red-Black Trees y no BST simples para el scheduler CFS?}
El Linux Kernel usa Red-Black Trees para el scheduler CFS (Completely Fair Scheduler) porque necesita garantizar que todas las operaciones de inserción, búsqueda y eliminación sean $O(\log n)$ en el peor caso. Un BST simple no ofrece esta garantía: con inserciones ordenadas se degradaría a $O(n)$, lo que causaría latencias impredecibles en un sistema operativo de tiempo real. El Red-Black Tree garantiza altura $\leq 2 \cdot \log_2(n+1)$ mediante sus invariantes de coloración y rotaciones locales. Esto es crítico para el scheduler, que debe insertar y eliminar procesos continuamente (en cada cambio de contexto) con latencia acotada y predecible.

\subsection*{5. ¿Cómo se podría aplicar un KD-Tree para indexar los centros poblados de los 109 distritos de la Región Puno?}
Un KD-Tree (K-Dimensional Tree) es una extensión del BST para datos multidimensionales. Para indexar los centros poblados de los 109 distritos de Puno por coordenadas GPS (latitud, longitud), se construiría un KD-Tree alternando la dimensión de partición en cada nivel: en el nivel raíz se divide por latitud, en el siguiente por longitud, luego nuevamente por latitud, etc. Cada nodo almacena las coordenadas de un centro poblado y particiona el espacio en dos mitades. Las consultas de cercanía (k-NN) se realizan en $O(\log n)$ promedio, descartando subárboles enteros usando la distancia mínima al punto de consulta. Esto permitiría responder preguntas como "¿cuáles son los 5 centros poblados más cercanos a una coordenada dada?" sin recorrer todos los puntos.

Los resultados muestran que C++ es consistentemente 5--10 veces más rápido que Python para todas las operaciones. Esta diferencia se debe principalmente a la ausencia de garbage collector en C++, el tipado estático que permite optimizaciones del compilador, y la gestión manual de memoria con RAII que evita sobrecargas de asignación. Python, por otro lado, ofrece mayor productividad para prototipado rápido y desarrollo interactivo. Para sistemas de tiempo real o embebidos donde cada microsegundo cuenta, C++ es la opción preferida. Para análisis exploratorio de datos y prototipado de algoritmos, Python sigue siendo más conveniente.
